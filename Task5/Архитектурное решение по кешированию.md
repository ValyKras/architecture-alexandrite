## 1. Мотивация
Операторы жалуются на медленную страницу MES; клиенты — на длительное выполнение заказов. Исходя из этого - требуется кешировать повторяемые запросы чтения списков заказов с фильтрами и пагинацией. Это уменьшит число одинаковых запросов к PostgreSQL и сократит время ответа MES API. Приоритетны: список заказов оператора, список заказов по статусу и очереди на назначение — только при подтверждении их частого чтения и достаточной повторяемости запросов.

## 2.Предлагаемое решение
Для решения проблемы можно внедрить серверный распределённый кеш Redis перед MES DB, управляемый MES API. Это единый кеш для всех экземпляров MES API и операторов, с централизованной инвалидацией, TTL и мониторингом. MES DB остаётся единственным источником истины.
Используя паттерн Cache-Aside кешируются только востребованные списки; запись остаётся простой и надёжной; при недоступности Redis чтение возможно из PostgreSQL - поэтому предлагается использовать именно паттерн Cache-Aside.
Паттерн Write-Through подходит хуже, поскольку одна запись статуса может изменить множество страниц и выборок, и синхронное обновление всех представлений дорого и сложно. Refresh-Ahead имеет смысл лишь для небольшого числа стабильных горячих выборок; для большого множества комбинаций фильтров приводит к ненужной фоновой нагрузке и не решает инвалидацию после записи.

Основная стратегия для кеширования — программная инвалидация по событию после коммита, реализованная через версионирование областей (generation keys), с TTL как страховкой.
При изменении статуса заказа список может поменять состав, сортировку, счётчики и пагинацию. Удаление одного кеш-ключа заказа недостаточно. На первом этапе использовать консервативную область: версию списков заказов в рамках организации/области доступа. После успешного коммита MES API атомарно увеличивает счётчик версии в Redis; новые чтения используют новый суффикс версии и не видят старые страницы. Старые значения удаляются по TTL. Если область слишком широка и hit ratio падает, позднее сузить её до статуса/оператора при доказанной корректности.

### Возможные стратегии:
| Стратегия | Плюсы | Минусы | Решение |
|---|---|---|---|
| Только TTL | Простая, восстанавливается после сбоев | До TTL отображает устаревший статус | Не использовать отдельно |
| Удаление точного ключа | Точная и дешёвая | Невозможно перечислить все комбинации списков без реестра | Недостаточно для списков |
| Программная инвалидация версии области + TTL | Учитывает фильтры, пагинацию, изменение состава списков | Может сбрасывать больше данных, чем нужно; нужна обработка отказов | **Выбрана** |
| Полная очистка Redis | Простая | Влияет на все функции и сервисы, создаёт всплеск нагрузки | Не применять |
| Только событие RabbitMQ | Подходит для асинхронных подписчиков | Возможны задержки, повторы, потери при неверной настройке | Использовать как дополнительный механизм, не единственный |

## 3.Альтернативные решения

| Параметр | Вариант A: Redis + Cache-Aside | Вариант B: клиентский кеш React / TanStack Query |
|---|---|---|
| Принцип | Общий кеш ответов MES API между операторами | Кеш запросов внутри браузера, дедупликация, stale-while-revalidate |
| Плюсы | Разгружает MES DB; общий для всех клиентов; централизованная инвалидация | Быстрый UX при повторном открытии; минимальные серверные изменения |
| Минусы | Дополнительная инфраструктура; риск устаревания; операционная поддержка | Не разделяется между операторами; слабее разгружает БД; сложная синхронизация изменений между пользователями |
| Риски | Проблемы согласованности и всплески при промахах | Пользователь видит устаревший статус до refetch |
| Подходит | Частые повторяющиеся серверные выборки и нагрузка на MES DB | Медленный UI при локальной навигации, но сервер не перегружен |

Вывод: для основной проблемы с повторными чтениями списка — вариант A. Вариант B можно добавить после него или вместо него, если метрики покажут, что проблема преимущественно в браузере, а не MES API/DB.
