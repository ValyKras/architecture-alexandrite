### Другие уровни ошибок
WARN — восстановимая ошибка: retry RabbitMQ, задержка ответа S3, временная недоступность зависимости, повторное сообщение, неуспешная бизнес-валидация, если она неожиданна.
ERROR — операция не завершилась: ошибка сохранения заказа, исчерпаны retries, сообщение попало в DLQ, не удалось рассчитать цену, 5xx. Обязательно error.code, exception.type, безопасное сообщение и stack trace для серверной ошибки.

## 2. Мотивация
Сейчас диагностика опирается на рассказ клиента, а история прохождения заказа через Shop API → RabbitMQ → MES API не восстанавливается централизованно. Это увеличивает MTTR, время поддержки, количество эскалаций и риск повторения ошибок. Корреляция логов и трасс позволит найти потерянное событие, ошибку обработки, зависшую очередь или отказ хранилища.

Цепочка жизненного цикла заказа именно Shop API → RabbitMQ → MES API, она так отвечает за передачу заказа в производство . Ошибка может возникнуть при записи заказа, публикации события, доставке, повторной обработке или изменении статуса MES. Наблюдаемость только одного сервиса не позволит локализовать проблему. CRM API, базы данных и S3 добавляются следующей волной; фронтенд — после настройки маскирования клиентских данных.

## 3. Предлагаемое решение

 В качестве системы логирования рекомендуется рассмотреть OpenTelemetry SDK (Java и .NET) + OpenTelemetry Collector для приёма OTLP, Vector или Fluent Bit для инфраструктурных логов, Grafana Loki для хранения логов, Grafana Tempo для трасс, Prometheus для метрик, Grafana и Alertmanager для визуализации и оповещений

### Политика безопасности
- Запрещено: ФИО, email, телефон, адрес, токены авторизации, cookie, пароль, платёжные данные, исходные тела запросов/ответов, бинарные 3D-файлы, presigned S3 URL. Исключения — только по согласованному перечню и с обоснованием.
- Допустимо: технические ID покупателя, заказа, оператора; при необходимости customer_id псевдонимизировать HMAC с секретом в защищённом хранилище. Не хешировать низкоэнтропийные персональные значения без ключа.
- TLS при передаче; шифрование хранилища; секреты в secret manager; централизованная маскировка в приложениях и Collector; запрет прямого доступа в Loki извне.
- RBAC: поддержка — ограниченный read-only доступ к бизнес-событиям по ID; разработчики — доступ к техническим логам своих сервисов; SRE — инфраструктурные логи; администраторы безопасности — аудит доступа. Production DEBUG — по заявке и с TTL.
- Аудит просмотров/экспортов, разграничение окружений, принцип минимальных прав, сроки удаления по политике компании и применимым требованиям законодательства.

### Предлагаемая политика:
 INFO/WARN — 30 дней онлайн; 
 ERROR — 90 дней; 
 DEBUG — 7 дней при временном включении; аудит безопасности — 180 дней в отдельном защищённом контуре, если это соответствует внутренним требованиям. 
 Traces — 7–14 дней, агрегированные метрики — 90 дней.

 ## 4. Сбор и анализ логов

 ### Дашборды
- Заказы: создание/мин, доля ошибок, p50/p95 длительности, переходы статусов, заказы без последующего статуса более SLA.
- RabbitMQ: depth, age of oldest message, unacked, redeliveries, DLQ, publisher confirms failures.
- MES: ошибки расчёта цены, длительность обработки, распределение назначений, задержка между созданием и началом производства.
- Инфраструктура: 5xx, latency, ошибки PostgreSQL/S3, заполнение буферов Collector, dropped logs/spans.

### Алерты
| Условие | Уровень | Действие |
|---|---|---|
| Доля 5xx Shop API > 5% за 5 мин и ≥ 100 запросов | critical | дежурный разработчик/SRE |
| В DLQ появились сообщения или oldest message > 10 мин | warning/critical по масштабу | проверить consumer, retry, зависимость |
| Не завершён путь заказа Shop → MES дольше 15 мин (при согласованном SLA) | warning | поддержка/ответственный за процесс |
| Ошибки расчёта MES > 2% за 10 мин при достаточной выборке | warning | MES команда |
| Collector dropped logs > 0 в течение 5 мин | warning | SRE |
| Нет телеметрии от критичного сервиса 5 мин при наличии трафика | warning | SRE |

Предусмотреть группировку по сервису и причине, дедупликацию, подавление повторов, maintenance windows, escalation policy и runbooks. Алертинг строить преимущественно на метриках/SLO, а не на каждой ERROR-записи.

### Аномалии
Для событий order.created и HTTP-запросов использовать базовую линию по часу дня/дню недели и rolling windows. Пример: вместо типичных 4 заказов/сек наблюдается 10 000/сек — это сигнал аномалии, но не доказательство DDoS. Сопоставить с RPS, уникальными клиентами, долей 4xx/5xx, IP/ASN (в защищённых security logs), успешными оплатами и очередями. При подтверждении — rate limiting/WAF/anti-bot на периметре; сбор логов сам по себе атаку не останавливает. Для всплесков настроить sampling технических INFO, но не терять критичные бизнес-события и ошибки.

## 4. Выбор технологии
| Критерий | Loki + Grafana | OpenSearch | Elastic Stack |
|---|---|---|---|
| Полнотекстовый поиск и сложная аналитика | умеренно, LogQL | сильные возможности | сильные возможности |
| Стоимость хранения большого объёма | обычно ниже при object storage и правильных labels | зависит от индексов/кластеров | зависит от лицензий и индексов |
| Эксплуатационная сложность | средняя | средняя/высокая | средняя/высокая |
| Корреляция с метриками и трейсами | сильная интеграция с Grafana/Tempo | требует настройки интеграций | сильная при использовании своего стека |
| Контроль кардинальности/индексации | важно проектировать labels | настройка mapping/shards | настройка mapping/shards |
| RBAC и multi-tenancy | зависит от внешнего auth/развёртывания | доступно, требует конфигурации | зависит от редакции/конфигурации |
| Лицензирование и vendor lock-in | open source, меньше зависимости | open source, экосистема | оценить условия лицензий |
| Скорость старта для команды | высокая при наличии Grafana | средняя | средняя |
