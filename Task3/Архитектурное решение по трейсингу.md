## 1.Анализ где может потеряться заказ 

| Участок | Возможный сбой | Что должно быть видно в трассе |
|---|---|---|
| Internet Shop → Shop API | таймаут/повтор запроса/дублирование заказа | запрос, идемпотентный ключ, результат создания |
| Shop API → Shop DB | ошибка транзакции, долгий SQL, запись не завершена | DB span, commit/rollback, длительность |
| Shop API → S3 | ошибка загрузки 3D-модели или недоступность файла | операция с объектом, код ошибки, длительность; без содержимого файла |
| Shop API → RabbitMQ | публикация не подтверждена брокером; сообщение не отправлено после commit | producer span, message_id, publisher confirm, outbox state |
| RabbitMQ → CRM API / MES API | очередь растёт, отсутствует consumer, TTL/DLX, повторная доставка | publish/receive/process spans, routing key, retry_count, DLQ |
| MES API → MES DB | ошибка обработки, блокировка, rollback, конфликт версий | обработчик, SQL/transaction span, результат изменения |
| MES API → RabbitMQ → Shop API/CRM API | статус изменён в MES, но событие не доставлено или не применено | сквозная связь order_id, event_id, trace/span links, статус доставки |
| CRM API и интерфейсы | устаревший статус, ошибки чтения или подтверждения заказа | HTTP spans и business events |

### Данные в трейсинге
- trace_id, span_id, parent_span_id, span.kind, service.name, service.version, deployment.environment, start_time, duration, status, error.type и безопасное описание ошибки.
- Корреляция заказа: order.id (внутренний непрямой идентификатор), order.status.from, order.status.to, order.event_id, order.version, workflow.step, processing.result, retry.count, idempotency_key (хеш или технический идентификатор).

## 2.Мотивация
Сегодня служба поддержки восстанавливает историю заказа по словам клиента, а инженеры вручную сопоставляют записи нескольких сервисов. Distributed tracing позволит найти путь конкретного заказа, видеть длительность этапов и место последнего подтверждённого действия. Однако сам по себе трейсинг не гарантирует обнаружения пропавшего сообщения: если операция вообще не началась, span может отсутствовать. Поэтому решение сочетает трейсинг с устойчивой доставкой событий, состояниями жизненного цикла заказа и контролем SLA.

## 3. Предлагаемое решение

- OpenTelemetry SDK / auto-instrumentation: Java для Shop API и CRM API; .NET для MES API. Автоматические HTTP/SQL/AMQP spans дополнить ручными бизнес-spans order.create, order.publish, order.consume, order.assign, order.status_change, order.confirm.
- OpenTelemetry Collector: приём OTLP по TLS, батчирование, ограничение памяти, фильтрация/редакция чувствительных атрибутов, экспорт в Tempo. При недоступности backend — ограниченная очередь/повторная отправка, с контролем потерь.
- Grafana Tempo: хранилище трасс; Grafana: поиск по trace_id и индексируемым атрибутам/связям. Для поиска по order.id обеспечить надёжный индекс/ссылку order_id → trace_id в операционном журнале событий или логах: поиск произвольного заказа только по Tempo без продуманной индексации может быть дорогим и неполным.
- Права доступа: Grafana/Tempo в закрытом контуре; TLS, SSO/OIDC, RBAC, аудит доступа.

### Автоматический мониторинг и алертинг
Добавить Order Lifecycle Monitor: подписчик на бизнес-события (или чтение достоверного журнала состояний) поддерживает order_id - текущий этап, время входа, deadline, последняя операция, event_id. Для каждого этапа конфигурируются допустимые сроки (например, ожидание передачи Shop→MES; ожидание назначения; ожидание производства). Точные SLA согласуются с бизнесом. Monitor экспортирует метрики в Prometheus, Alertmanager уведомляет on-call/поддержку, а Grafana связывает событие с trace_id.

## 4.Компромиссы

| Ограничение | Последствие и решение |
|---|---|
| Потерянное до создания span сообщение | трейс не покажет несуществующий span; нужны outbox, confirms, DLQ и журнал событий |
| Асинхронная обработка может длиться дни | один гигантский trace не нужен; связывать trace через `order_id`, `event_id` и span links |
| Sampling и срок хранения | не все запросы будут доступны; бизнес-журнал без sampling |
| Проприетарные системы / неподдерживаемые клиенты | потребуются адаптеры, возможно дорогая доработка; использовать boundary spans |
| Высокая кардинальность `order.id` | не превращать order_id в Prometheus label; хранить в traces/журнале с ограниченной индексацией |
| Накладные расходы и стоимость Tempo | лимиты атрибутов, sampling, retention, контроль бюджета |
| Трейсинг ≠ гарантия доставки | отдельно внедрять transactional outbox/inbox и контроль очередей |
| Точное состояние заказа распределено между БД | определить авторитетный источник каждого этапа и правила сверки статусов |

## 5.Аспекты безопасности
1. Grafana и Tempo доступны только из корпоративной сети/VPN; административные API и OTLP endpoints не публикуются в интернет. Внутренние соединения — TLS, где применимо mTLS.
2. Аутентификация через корпоративный SSO/OIDC, MFA для администраторов; RBAC: поддержка — ограниченный просмотр трасс по заказам, разработчики — трассы своих сервисов, SRE — эксплуатация, администраторы — конфигурация. Разделять prod/test.
3. На уровне SDK и Collector — allowlist атрибутов, маскирование секретов, запрет тел запросов/ответов, персональных данных, payload RabbitMQ, URL с токенами, SQL-параметров; регулярные проверки на утечки.
4. Шифрование при передаче и хранении, управление ключами/секретами, аудит поиска и доступа, ограничение выгрузки, retention и удаление согласно политике компании.
5. Для поддержки использовать безопасный поиск по внутреннему order_id; не выдавать клиентам прямые ссылки в Grafana и не раскрывать технические детали.
